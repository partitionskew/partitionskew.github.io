Introduction#

By default, traffic between pods in a k8s cluster is non-isolated [1]. This means all incoming and outgoing connections are allowed, including those originating outside of the cluster. With the appropriate container networking plugins installed, Network Policies can secure both ingress and egress traffic.

In this brief article, we describe what network policies are and give a couple simple examples of how to use them.

Kubernetes Network Policies#

Network policies only take effect if the appropriate network plugin is installed. Check the documentation for a list of supported plugins [2]. Common choices include Calico and Cilium. Note that features and behaviour are not equivalent across network plugins.

Network policies control UDP/TCP traffic at the L3/L4 layer (IP addresses & ports). The network policy selects a set of pods via the podSelector [3]. For matching pods, the policy permits ingress and/or egress traffic from/to:

  1. pods
  2. namespaces
  3. IP blocks

For example, a network policy permits pod A in namespace foo to make an outgoing connection to pod B in namespace bar. A separate network policy must permit pod B to accept traffic from pod A in namespace foo otherwise the connection will not be allowed.

Of course, it is possible pod A doesn’t have a network policy which means it can make any outgoing connection. Likewise, pod B may not have a network policy in which case it accepts all incoming connections.

Network policies are additive. By default, traffic is not restricted. However, you can add a network policy that blocks all ingress & egress traffic. Then you can selectively permit one or more incoming/outgoing connections as required following the principle of least privileges.

Gotchas#

Vanilla k8s network policies do not support:

  • cluster-wide scope
  • targeting k8s Service objects
  • TLS traffic
  • audit logs
  • deny permissions

Traffic on the same host is always permitted regardless of what network policies are applied to the pod.

Additionally, it takes time for a new network policy to take effect. If a pod exists before the network policy, then its traffic is effectively unsecured. Moreover, it is not defined what happens to an existing connection if a new network policy would deny it. It depends on the specific network plugin and it’s recommended to avoid modifying policies that affect existing connections.

Make sure your pods are resilient to lost connections. Use retries with exponential backoff.

Examples#

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: foo
spec:
  podSelector: {} # all pods in foo namespace
  policyTypes:
    - Ingress
    - Egress

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-ingress
  namespace: bar
spec:
  podSelector:
    matchLabels:
      appName: my-server
  ingress:
    - from:
      - podSelector:
          matchLabels:
            appName: my-client
      - namespaceSelector:
          matchLabels:
            name: foo
      - ipBlock:
          cidr: 1.2.3.0/24
  policyTypes:
    - Ingress

Cilium Network Policies#

Cilium is a networking solution that extends the capabilities of the basic k8s Network Policy. Cilium introduces the CiliumNetworkPolicy and CiliumClusterwideNetworkPolicy custom resource definitions (CRDs).

Unlike the basic NetworkPolicy resource, Cilium network policies support policies at L3 and L7. This means you can target services by name when permitting ingress or egress traffic.

To learn more about Cilium network policies, refer to the documentation: https://docs.cilium.io/en/stable/security/policy/index.html

Conclusion#

Kubernetes network policies enforce ingress and egress traffic using TCP/UDP protocol at L3/L4 of the network stack. Network policies are installed on a per-namespace basis and apply to the selected pod(s).

Network policies are additive and allow incoming or outgoing connections. If a connection is not explicitly allowed, then it’s denied.

Vanilla policies have some limitations which are addressed in external solutions such as Cilium. Without policies, all incoming and outgoing traffic is permitted which is not secure.
